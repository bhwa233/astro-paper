# 不要写的十三类测试

每一条在你写的当下都看起来挺合理。**写测试之前读，不是写完再读。**

每条三段：**写法** / **为什么看着合理** / **它实际漏掉什么**。
第三段是判据——一个测试的价值等于它能抓到而其他 gate 抓不到的回归。

---

## 1. stub 打 stub

**写法**：把两个协作方都注入成 stub，然后断言调用顺序，以及 stub 自己的返回值。

**看着合理**：隔离得很干净，跑得飞快，没有外部依赖。

**漏掉**：没有任何生产代码在跑。它通过是因为两边都是你写的。
被测对象整个删掉换成一个空实现，它还是绿的。

## 2. 自我比较

**写法**：断言一个工厂函数等于它内部调用的那个函数；或者用被测函数
算出期望值再和它自己比。

**看着合理**：期望值总是对的。

**漏掉**：断言只是把实现复述了一遍。实现错了，期望值跟着一起错。
判据见 `tests-earn-their-place.md` 的「把实现遮住」。

## 3. 复述常量

**写法**：

```
expect(SOME_CRON).toBe('15 */6 * * *')
```

同类：cookie 名、超时值、分片大小、版本号。

**看着合理**：这些值很重要，改错了后果很严重。

**漏掉**：断言和源码是同一次编辑改的。「改一个而不改另一个」这种事根本不会发生，
所以它抓不到任何东西。真正的风险是这个值本身取错了——而这条断言对此一无所知。

## 4. 写死数量

**写法**：

```
expect(items).toHaveLength(557)
```

同类：「某年某月某日测得」的 fixture 行数。

**看着合理**：数量变了说明有东西被误删了。

**漏掉**：任何合理的新增都会打破它。于是它训练出的习惯是：
不读失败原因，直接改数字。等到某天真的误删了，那个数字也会被直接改掉。

改成断言下界（非空、至少 N 条）或结构性质。

## 5. 对源码文本做断言

**写法**：读一个源文件，然后正则匹配某个指令、装饰器或字段名。

**看着合理**：这确实是一条该被强制的规则，而且写起来很快。

**漏掉**：改个名字它就挂；而一个保留了该字符串的真实回归它却放行。
它测的是文本，不是行为。

如果这条规则值得强制，写成扫全目录的 checker 脚本——见 `verification-gates.md`。

## 6. 证明「东西被注册了」

**写法**：断言路由出现在生成的文档里、handler 出现在派发表里、
插件出现在插件列表里。

**看着合理**：注册漏了确实是个真实故障。

**漏掉**：注册漏了的话，那条路由的功能测试也会挂——如果它有功能测试的话。
如果它没有功能测试，说明它不重要到需要测；那也不重要到需要断言它注册上了。
**如果这条路由重要，就测这条路由。**

## 7. 让 schema / 校验库测它自己

**写法**：只测能通过的解析用例；或者构造一个带类型的字面量，再把字段读回来断言。

**看着合理**：schema 是数据契约，当然该测。

**漏掉**：那里唯一真实的检查是编译期类型标注，而类型检查已经在跑了。
你在验证 schema 库的作者会不会写解析器。

值得测的是**你自己加的细化规则**——自定义校验、跨字段约束、
以及被拒绝的输入长什么样。

## 8. 断言第三方的输出

**写法**：断言某个库序列化出的结构、生成的 SQL 文本、发出的请求体长什么样。

**看着合理**：这是我们真实发出去的东西。

**漏掉**：你在测别人的发布说明。库升个小版本改了字段顺序，
测试红了，而我们的行为完全没变。

## 9. mock 上游再断言我们的输出格式

**写法**：mock 掉外部 API，喂一份固定响应，然后断言我们返回的结构长什么样。

**看着合理**：生产代码确实在跑，覆盖率也确实上去了。

**漏掉**：断言的内容是「我们喂进去的 mock 出来长什么样」。
上游字段一变——也就是真实故障发生的那一刻——要改的是 mock 而不是断言，
测试从来不会因为真实回归而变红。

**唯一值得写的例外**：**我们对上游异常的反应**——超时降级、缺字段兜底、
多源回退时选了哪一个。一个上游一条，断言分支走向，不断言输出字符串。

## 10. 测脚手架

**写法**：给模板生成的样例路由、样例表、样例组件写测试。

**看着合理**：它在代码库里，它没有测试。

**漏掉**：它没有调用方。你在测模板作者的代码。
**删掉脚手架比给脚手架写测试便宜。**

## 11. 同一段代码的重复穿越

**写法**：一个「连续失败就暂停」的守卫，写成八条用例——触发、各种原因、
已暂停不重复、忽略可重试、计数去重、暂停后不派发……
同类：一个列表端点，每个排序列、每种筛选组合各一条。

**看着合理**：每条用例的名字听起来都在描述一个不同的场景。

**漏掉**：守卫只有一个，那八条走的是同一段代码。
它的边界值得两三条：触发、不触发、以及触发后的副作用。其余是重复穿越。

列表端点值得一条——鉴权，或者「未知排序列不会变成注入」——
不值得每种组合各一条。那些是 SQL 拼装断言。

## 12. 文案快照

**写法**：对用户可见文本做快照断言。

**看着合理**：文案改动应该被注意到。

**漏掉**：文案就是要改的。快照红了之后唯一的操作是更新快照，
所以它等价于没有断言，但要付出每次改文案都要重跑更新的代价。

跨语言的 key 结构一致性用 checker 脚本强制，那才是会真正坏掉的部分。

## 13. 在测试里维护第二份 schema

**写法**：把几百行建表语句从 migration 抄进测试的 setup。

**看着合理**：测试需要一个数据库，而跑真实 migration 很慢。

**漏掉**：它会随 migration 漂移，且没有任何东西会告诉你它漂了。
测试通过，生产失败。

要么在 setup 里跑真实 migration，要么只建被保留用例真正需要的那几张表。
**不要维护第二份 schema。**

---

## 附：没有 DOM 的环境

如果测试运行在没有 DOM 的运行时里，不要为了断言某个组件渲染出某个字符串
而引入一整套 DOM 环境。那是一个信号：**这个行为应该抽成一个纯函数**，
让组件和测试都调用它。组件本身的正确性由类型检查、lint 和构建覆盖。
