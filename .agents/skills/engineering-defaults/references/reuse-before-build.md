# 造之前先复用

在写组件、hook、工具函数或格式化器**之前**读，不是 review 时读。

这份文件要防的失败模式是：在一个已经装好这四样东西、已经接好主题、已经处理过
无障碍、暗色模式也已正确的仓库里，用裸输入框加四十行 CSS 拼一个搜索框、
用三个下拉拼一个日期选择器、用一个 fixed div 拼一个浮层通知。

手搓的版本永远只覆盖 happy path。缺的是键盘操作、焦点管理、屏幕阅读器标注、
暗色模式、右到左、时区、闰秒、输入法组合、滚动锁定——这些恰好是没人会为它写测试的部分。

## 决策梯

依次往下，命中就停。

1. **本仓的共享原语里已有？** 直接用。
2. **已装依赖里已有？** 直接用。为一件已装依赖已经能做的事再引入第二个库，
   属于会被打回的改动。
3. **仓库别处已有**——某个 hook、helper、同类组件在做同样的事？提取或复用它，
   而不是并排再写一份。
4. **存在成熟且在维护的开源库？** 连同**包名**、**为什么已装的这批覆盖不了**、
   **维护状态**一起提出，等决策后再加依赖。
5. **手写。** 最后手段。留一条注释说明你查过什么、为什么都不合适。

原生元素在语义确实更简单时完全可以用——段落、列表、行内文本。
这条规则针对的是**控件和行为**，不是禁用原生 HTML。

## 第 4 步：怎么算「成熟且在维护」

提名之前核对，别凭印象：

- 最近一次发布距今多久；仓库有没有在回应 issue
- 打包体积，以及它是不是会把一整套子依赖拖进来
- 类型定义是自带还是靠第三方补
- 许可证与本仓兼容
- 它解决的是不是你**当下**的问题，而不是它顺带能做的另外十件事

一个不再维护但接口稳定、代码量小的库，可以是合理选择——把这个判断写出来，
别假装它还活着。

## 第 5 步：手写时的义务

注释里写清三件事，写在实现上方：

```
// 查过 <已有原语>：<为什么不够>
// 查过 <候选库>：<为什么不合适——体积/维护/接口/许可证>
// 因此手写。范围仅限 <明确的边界>。
```

没有这条注释，下一个人只能重做一遍同样的调研，
或者更常见的——直接假设你没查过，把它替换成一个库。

## 尤其别手搓的行为

这些每一个都有已经解决好的实现，而且难点都不在主流程：

| 行为 | 难在哪 |
| --- | --- |
| 浮层通知 / toast | 队列、去重、焦点不被抢、超时暂停 |
| 日期与时间输入 | 时区、本地化格式、键盘操作、区间选择 |
| 可搜索选择 / combobox | 焦点管理、虚拟滚动、无障碍角色标注 |
| 命令面板 | 全局快捷键、模糊匹配、滚动到选中项 |
| 模态与确认框 | 焦点陷阱、返回键、滚动锁定、层叠 |
| 长列表虚拟化 | 变高行、滚动锚定、跳转到指定项 |
| 拖拽排序 | 键盘等价操作、自动滚动、触屏 |
| 富文本 / 代码编辑 | 输入法组合、撤销栈、粘贴清洗 |
| 精确小数运算 | 二进制浮点在比较、排序、舍入上的行为 |
| 日期算术 | 夏令时、月末、周起始日 |

## 封装边界

第三方库经一层内部封装使用，业务调用点不直接引：

- 换库、加默认值、统一错误处理时，改动面是封装那一个文件
- 封装是放本仓约定（主题 token、错误格式、日志）的唯一地方
- 「哪里用到了这个库」变成一个可回答的问题

例外是那些本来就是语言级基建的库——类型工具、断言库。给它们套壳只是增加一层。

## review 时问的

- 这个新组件在共享原语里有没有近亲？
- 这个新依赖和已装的哪个功能重叠？
- 手写的那段有没有那条注释？
- 第三方是从封装引的，还是从调用点直接引的？
