# 什么时候一个测试值得写

## 闸门

写测试之前，依次回答：

1. **它是否命中下面四种情形之一？**
   否——不要写。改为说明你验证了什么（见 `verification-gates.md`）。
2. **它是否命中 `do-not-test.md` 里的任何一条？**
   是——不要写，哪怕它看起来同时也命中第 1 条。
3. **这个行为是不是已经在别处被断言过了？** 先搜。如果是，
   去加强那个已有用例，而不是并排再加一个。
4. **这是能证明它的最低层吗？** 同样的逻辑，纯函数测试优于集成测试；
   集成测试则只断言集成层额外做的那部分。
5. **它是不是某个已有分支机制的第 N 个代表？** 是的话不要写——见下面「分支用代表制」。
6. **为了让它跑起来，需要搭多大的脚手架？** 如果要 mock 一个上游、
   手写一份 schema、或者铺几十行 fixture 才能断言一句话，先回到第 1 条重新算账。

## 四种情形

不属于其中任何一种，就不要写。

### 1. 存在会写错的真实逻辑

数学、解析、日期时间处理、格式化、查询构造、排序与排名、状态机转移——
任何一个看似合理的实现可能悄悄不正确的地方。

判据：**把实现遮住，你能不能独立说出正确答案应该是什么。** 能，就有真实逻辑。
如果正确答案只能靠读实现得出，那你要写的是自我比较。

接线、传参、重导出、把 A 的字段搬到 B——不算逻辑。

### 2. 有 bug 上过线

把它钉住。并在用例上方的注释里写清事故：**什么坏了，错误行为是什么。**

注释才是重点——没有它，下一个读者无法判断这条断言是否还有意义，
于是它会在下一次重构里被顺手改成通过。

### 3. 不变量跨越并发、状态或真实外部依赖

租约、配额、重试、幂等、暂停与恢复、游标推进——那些你读一个函数看不出来的行为。

这是测试最明显值回成本的一种情形，因为失败模式只在交错执行时才出现，
而人工验证基本不可能触发它。

### 4. 信任边界必须成立

服务端自己重新计算而不是相信请求。鉴权拒绝。校验拒收。越权访问被挡。

**每个边界一个用例，不是它后面每条路由一个用例。**

## 一个行为，一次证明，最低层

一个中间件需要一个鉴权拒绝用例，不是每条受保护路由一个。

如果纯函数层已经覆盖了某个计算，上层测试只断言上层**额外**做的事——
它重新计算而不是相信调用方。

加用例之前先搜这个行为。如果别处已经断言过了，去加强那一条。

## 分支用代表制

当一段代码有 N 个同构分支（模式、方法、约定、时机、地区），覆盖的目标是
**每种分支机制各一个代表**，不是每个取值各一条。

第 87 个分支和第 2 个走的是同一段派发代码——它们一起坏、一起好。
各取一个值，证明这套开关接得通，就够了。

只有当某个分支有**自己独占的逻辑**——不同的公式、不同的法规常量、
不同的上游、不同的失败模式——它才值得单独一条。

## 批量生成的用例

遍历注册表、目录、配置表，应该写在**一个**用例里，循环放在里面，
并在每条断言消息里带上标识符——而不是用循环生成几百个用例。

断言**结构**，以及「这东西能跑」。不要为每个条目钉一个黄金输出字符串——
那是把配置文件复制到测试里，配置一改两边都要改，而它从来不会独立地红。

## 规模是信号

单个测试文件超过约 300 行，通常意味着它在做三件不同的事。
拆开之前先问哪一件其实不该测。

拆完之后的健康形状是分层，每层职责单一：

| 层 | 职责 | 允许出现具体数值吗 |
| --- | --- | --- |
| 纯函数 / 公式 | 最低层的计算 | 是，这里是数值的家 |
| 注册表 / 目录 | 结构完整性、默认值能跑通 | 否 |
| 引擎 / 派发 | 拒绝承诺 + 分支接得通 | 否 |
| 常量表 | 外部规定的常量（法规、协议、格式） | 是，值就是产品 |

往「注册表」层里塞数值，是测试文件长到一千行的最常见路径。

## 删除测试

删掉一个命中 `do-not-test.md` 的测试是合理且受欢迎的改动。删除时：

- 检查有没有脚本按路径点名了它
- 检查它是不是唯一让某个模块对死代码检测保持可达的入口
- 在提交信息里说明这个测试原本在断言什么，以及为什么那条断言不成立

**不要因为一个测试在失败就删掉它。** 失败的测试要么是真实回归，
要么是错误的断言；判断是哪一种，并说出是哪一种。
