# 不写测试时，什么算验证过

「不加测试」不等于「不验证」。它等于**换一种更便宜、覆盖面更宽的验证方式，
并把它说出来**。

## gate 就是验证

一个改动如果已经被下面这些覆盖，那**就是**验证。说明这一点然后往下走：

| gate | 它真正保证了什么 |
| --- | --- |
| 类型检查 | 接线正确、字段存在、签名匹配、重构没有漏改调用点 |
| lint | 违规写法、未使用导出、可疑模式 |
| 构建 | 整棵依赖图能解析、边界规则成立、产物能生成 |
| 结构化 checker | 项目自定的跨文件规则（见下） |
| 死代码检测 | 新增的东西真的被接进去了 |
| 对真实端点发一次请求 | 端到端接得通 |

绝大多数「接线类」改动——加字段、改 prop、重导出、改配置——
在类型检查和构建之外，测试能加的信息量是零。

## 结构化 checker 优于测试里的文本断言

一条规则如果值得强制，写成扫**全目录**的脚本，跑在 lint 阶段：

- 它对新文件自动生效，而测试只覆盖你想起来的那个文件
- 它的失败信息能直接指出违规位置
- 它不会因为改名而误报

适合写成 checker 的：边界规则（哪些文件不能引入哪些东西）、
命名与目录约定、跨语言资源的 key 结构一致性、必需的元数据字段。

不适合写成 checker 的：任何需要执行代码才能判断的东西。那是测试的地盘。

## 挑最小的有意义 gate

不要每次改动都跑全套。按改动性质挑：

- 纯类型 / 接线改动 → 类型检查
- 新增或改动源文件 → 类型检查 + lint
- 动了模块边界、构建配置、产物形状 → 加构建
- 动了跨文件约定 → 加对应的 checker
- 动了真实逻辑 → 前面这些，再加上那条值得写的测试

## 汇报纪律

- **gate 没跑或没通过，就不许把改动描述成已验证。** 「应该没问题」和
  「类型检查过了」在读者眼里长得一样，但只有后者可复核。
- 测试或 gate 失败就直说，并引用失败输出里**最短的决定性一行**。
  不要粘贴整段日志，也不要只说「有些失败」。
- 说清证据来自哪个环境：本地、预览、还是生产。
  本地构建的输出不能用来声称生产可见。
- 跳过了某个 gate 就说跳过了，以及为什么。
- 手动验证过就写清楚验证的是什么：哪个路由、什么输入、看到什么。

## 常见的自欺

| 说法 | 实际情况 |
| --- | --- |
| 「逻辑很简单，不会错」 | 类型检查花几秒就能证明它至少接得通。跑一下。 |
| 「我加了测试，所以验证过了」 | 如果那个测试命中 `do-not-test.md`，你只是增加了一个维护项。 |
| 「构建过了，所以功能是对的」 | 构建证明能跑，不证明算得对。真实逻辑还是需要那条测试。 |
| 「本地看着是对的」 | 说清是哪个环境、哪个路由、什么输入。 |
