# 微博热搜每日文章技术方案

状态：astro-paper 管线已实现，已完成首次 CI 验收
最后更新：2026-08-19

## 1. 背景

目标是每天产出一篇微博热搜的中文整理文章，形态对标刚上线的 `reddit-trending`：榜单只是入口，真正的内容来自对每个话题的展开。

原始设想是三步：拉取 `bhwa233/weibo-trending-hot-history` 的当日热搜前 20 条非广告词条 → 逐条打开微博智搜（`s.weibo.com/aisearch`）取 AI 结论 → 再用模型逐条摘要，由代码拼成短条目文章。

调研结论：第一步和第三步没有问题；第二步成立，但**必须带登录态**——智搜没有任何匿名或访客态的入口，详见第 3.2 节。方案据此确定为「智搜是硬要求、不设降级」，见第 4 节。

## 2. 目标与非目标

目标：

- 每个归档日最多一篇文章，走现有 `blog-publish.yml` 通道，与其他任务共用归档、校验与提交
- 榜单只作筛选依据，正文必须讲清楚每个话题的来龙去脉与争议
- 保留上游榜单顺序，话题不做事件级合并
- 取不到任何完整智搜结论的当天跳过

非目标：

- 不做实时热搜推送，不追求与微博榜单同步
- 不抓取微博正文与评论区的原始内容；正文证据只来自智搜结论
- 不提供任何降级来源：智搜取不到就丢话题，不用导语或热度数据凑（见第 4 节）

## 3. 调研结论

以下三条均为 2026-08-19 实测，不是推断。

### 3.1 数据源可用，且比预期干净

不需要爬 `archives/*.md`。仓库 `master` 分支提供结构化 JSON，`raw.githubusercontent.com` 匿名可取：

```text
api/<date>/summary.json   当日累积榜，每小时更新
api/<date>/NN.json        逐小时快照（00.json … 23.json）
```

`summary.json` 字段：

```json
{
  "title": "宇树科技中签女子开盘就卖出",
  "category": "社会",
  "url": "https://m.weibo.cn/search?containerid=...",
  "description": "8月19日，人形机器人概念股宇树科技正式登陆科创板……",
  "hot": 2110760,
  "ads": false,
  "readCount": 34965000,
  "discussCount": 5918,
  "origin": 997
}
```

2026-08-19 当日 252 条。`ads` 可直接滤掉推广位；`description` 并非每条都有，但存在时已经是一句话摘要。分类分布：社会 90、暂无 39、明星 36、电视剧 10、综艺 10、财经 8、汽车 6、情感 5。

**注意 `summary.json` 是当日累积而非某一时刻的快照**，12:00 读取只覆盖 00–12 点。

### 3.2 微博的反爬是三级墙，不是一道

把三级混为一谈会做出错误的技术选型。以下均为 2026-08-19 实测：

| 级别 | 代表端点 | 匿名 curl | 无头浏览器（未登录） | 需要 |
| --- | --- | --- | --- | --- |
| 公开 | `m.s.weibo.com/topic/detail?q=…` | **200**（9KB） | 200 | 无 |
| 访客态 | `m.weibo.cn/api/container/getIndex?…realtimehot`（热搜榜） | 302 | **通过** | 浏览器执行访客 JS |
| 登录态 | `s.weibo.com/aisearch?q=…` | 302 | 访客验证通过后 → `passport.weibo.com/sso/signin` | **已登录账号** |

补充实测：

- `s.weibo.com/weibo?q=…`（站内普通搜索）与智搜同级，同样撞登录墙。
- `m.weibo.cn/aisearch?q=…` 访客验证能自动通过，但页面返回 **404**——移动端没有智搜路由，不存在「换移动端绕过登录」的余地。
- `m.s.weibo.com/aisearch`、`s.weibo.com/ajax/aisearch`、`m.s.weibo.com/ai/search` 均 302 到 `weibo.com/sorry?pagenotfound`；`weibo.com/ajax/side/aisearch` 返回 403。**没有公开的智搜 JSON 接口。**

所以智搜只能靠**已登录账号**抓取。服务端具备这个能力（`rain-api-weibo-browser.service` 提供的专用 Chrome，`weibo.py` 已在用），接口方案见 `yt_dlp_fastapi/docs/weibo-aisearch-endpoint.md`。

**仍未验证**：智搜结论是服务端渲染还是前端流式生成、选择器长什么样。这需要在有登录态的机器上跑一次才能确定。

### 3.3 上游仓库正是靠前两级绕开了登录

`weibo-trending-hot-history` 全程不碰 `s.weibo.com`，所以它在 GitHub Actions 里每小时跑而不需要任何 secret：

- **热搜榜**：无头 Playwright + iPhone UA 导航到 `m.weibo.cn/api/container/getIndex?…realtimehot`，让浏览器自己跑完访客验证的 JS，再从 `body` 读 JSON。
- **话题详情**：`m.s.weibo.com/topic/detail?q=<title>` 用纯 `fetch`，cheerio 解析出分类、导语、阅读数、讨论数、原创人数。

`summary.json` 里的 `description` / `readCount` / `discussCount` / `origin` 就来自第二个端点。这意味着**话题导语是匿名可取的**，构成智搜之外的一条零风险证据来源——但覆盖率不足，见 3.4。

### 3.4 话题导语覆盖率只有三分之一

2026-08-19 的 252 条里只有 93 条带 `description`（36%），**前 20 条里只有 8 条**。质量也参差：既有「8月19日盘中，人形机器人板块持续走低，同花顺人形机器人指数大跌近5%」这类带数字的事实，也有「我又磕到了！昀牵孟绕~」这类粉丝短语。

因此「只用导语」撑不起一篇有内容的文章。

### 3.5 同题事件可能重复

2026-08-19 的榜单里，四川升学宴事故一个事件占据 #1（四川一升学宴突发事故5人死亡）、#2（致5死升学宴主家本不想办）、#12（升学宴致5死17伤主家亲属发声）三个位置。当前任务刻意保留热搜榜的原始顺序，不做事件级合并。

## 4. 路线：智搜为唯一证据来源，不设降级

**已定：走登录态抓智搜，且智搜结论是硬要求。** 一个话题拿不到完整的智搜结论就直接落选，不用话题导语或热度数据顶替。

不设降级的理由：下游模型拿到的每一段文字都会被当成智搜结论写进文章。一个静默的替代品会让文章声称的来源与实际来源不符，这比少一条选题严重得多。同理，半截的生成结果也一律丢弃——被截断的 AI 结论读起来仍然通顺，下游没有任何办法识别它缺了后半段。

代价必须认下来：

- 把一个真实微博账号放进了日更链路。账号被风控时故障表现为跳登录页，不是 HTTP 错误，必须显式识别（见 7 节）。
- 每天 N 次带登录态的搜索请求，N 直接等于风控暴露面。
- 智搜不稳的那天，文章条目数会减少；全部失败时当天不发稿。

已否决的两条：**只用公开数据**（`summary.json` + `m.s.weibo.com/topic/detail` 导语）证据太薄，导语覆盖率仅 36%、前 20 条仅 8 条，写出来是流水账；**榜单加站外公开报道**能绕开登录且事实密度够，但引入新的抓取面与信源质量判断，工作量远大于前者，暂不考虑。

## 5. 数据流

```text
raw.githubusercontent.com/bhwa233/weibo-trending-hot-history/master/api/<date>/summary.json   ← 匿名，TS 侧直接拉
  └─ 规则层：滤 ads，保留上游顺序前 50 条
       └─ GET /v1/weibo/aisearch                      ← 服务端，走已登录 Chrome
            └─ 逐条取智搜结论；取不到的话题直接丢弃，不顶替
                 └─ 模型：逐条摘要 + 基于最终收录话题生成标题后半句 → 代码拼短条目
                      └─ archivePost → blog-publish.yml
```

榜单 JSON 匿名可取，所以只有智搜那一步需要服务端，且它是同步 GET，不需要作业与轮询。

博客侧新增 `weibo-trending` 任务，落点与 `reddit-trending` 完全一致：`BLOG_TASKS` 一条、`SOURCE_BUILDERS` / `SOURCE_COMBINERS` / `LEDGER_APPENDERS` / `ARCHIVE_FORMATTERS` 各一项、逐条摘要与整篇标题提示词、一个 `publish-*.yml`。

站点文章发布成功后还会进入独立的[微博热搜微信草稿管线](./weibo-trending-wechat-pipeline.md)：它只读取已提交文章，保留前 10 条并通过纯规则渲染为一张 Top 10 总封面加 10 张话题卡，不再调用模型。

## 6. 已定决策

1. **内容范围。** 输入固定为上游顺序中的前 50 条非广告话题，不经过模型选题或政治/政策排除。
2. **时间窗。** 每日北京时间次日 00:20（UTC `20 16 * * *`）读取前一天的完整累积榜，归档日期为前一天。
3. **条目数量。** 不设备选池和最低发布数。前 50 条逐条智搜，失败即丢弃且不向第 51 条以后补位；只要有一条成功即发布，全部失败才跳过当天。
4. **文章形态。** 正文沿用 Reddit 热搜的二级标题短条目风格，每条输出话题名、指向原始微博 URL 的短锚文本和模型对智搜结论的摘要。摘要不设长度上限，不做整篇二次生成。标题固定为 `<date> 热搜 ｜ <AI 标题后半句>`；后半句只基于最终成功收录的话题生成一次，并作为 source 证据传给归档层。

## 7. 风险与失败处理

没有降级路径，所以每一种失败都只有两个去向：**丢掉这个话题**，或**当天不发稿**。

- **登录态失效**：表现为跳转登录页而非 HTTP 错误，必须显式识别并报错，不能把登录页当内容解析。`weibo.py` 已有 `_is_visitor_challenge_url` 的先例，但它只覆盖访客验证，不覆盖 `sso/signin`。这一项会让当天全部话题落选，等价于停更，因此要能从日志一眼看出是登录问题。
- **智搜生成为流式**：需要明确的「生成完毕」判据。判据不可靠就会产出半截结论，而半截结论读起来通顺、下游无法识别——所以未收敛一律丢弃，不返回部分结果。
- **单条取不到**：该话题丢弃，不用任何其他来源顶替，也不从榜单第 21 条以后补位。
- **全部失败**：当天跳过；只要保留一条完整智搜结论及摘要，就照常发布。
- **标题生成失败**：标题后半句通过 JSON 与长度校验重试；重试耗尽则当天生成失败，不回退到无主题标题。

## 8. 上线前置条件

`astro-paper` 已实现任务注册、来源组合、归档契约及 `Publish Weibo Trending` 工作流。微博智搜与 Reddit 来源复用同一个服务根地址及 Bearer token：工作流将现有 `REDDIT_SOURCE_API_URL`、`REDDIT_SOURCE_API_TOKEN` 映射为微博任务所需的运行时变量，无需新增 GitHub secret。首次运行前仍需：

1. 在服务端对真实话题调用一次 `GET /v1/weibo/aisearch?url=...`，确认 OpenCLI 登录会话和页面选择器能返回完整 `answer_markdown`。当前服务实际接口使用完整智搜 URL 参数，不提供旧方案中设想的 `debug=true` 返回。
